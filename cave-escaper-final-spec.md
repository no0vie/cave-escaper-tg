# Cave Escaper — финальная спецификация проекта

## 1. Концепция

**Cave Escaper** — многопользовательская приключенческая игра для Telegram, реализованная в виде Telegram-бота.

Игроки исследуют процедурно генерируемую карту внутри общего Telegram-чата.

Каждый игрок создает персонажа через личный диалог с ботом.

Основная модель взаимодействия:

- **Telegram-чат = игровое пространство**
- **Личный диалог с ботом = личный интерфейс персонажа**

Игроки перемещаются по карте, исследуют помещения, находят предметы, используют и изнашивают оборудование, встречаются друг с другом и пытаются найти выход.

Карта периодически полностью перестраивается.

Главная идея:

> Игрок не читает заранее написанный квест. Он находится внутри постоянно меняющегося мира и сам создает историю своими действиями.

---

# 2. Технологический стек

Использовать:

- Node.js 22 LTS или новее;
- TypeScript;
- grammY для Telegram Bot API;
- PostgreSQL;
- Drizzle ORM;
- Redis;
- BullMQ для фоновых задач;
- Docker;
- Docker Compose;
- Vitest для unit/integration tests.

Все зависимости должны иметь актуальные стабильные версии на момент генерации проекта.

## Архитектурный принцип

Telegram Bot API не должен содержать игровую логику.

Игровой движок должен быть независимым от Telegram.

```text

   ▼
```

# 4. Создание игры

Команда:

```text
/game
```

При первом запуске:

1. определить Telegram Chat ID;
2. определить пользователя;
3. назначить его владельцем;
4. создать GameRoom;
5. создать карту;
6. установить настройки;
7. показать инструкцию игрокам.

Пример:

```text
🕳️ CAVE ESCAPER

Игра создана.

👥 Игроков: 5
🗺️ Размер карты: 25 клеток
🚪 Вход найден
🏁 Выход существует

Создайте персонажа через личный диалог со мной.
```

---

# 5. Игроки

Игроком считается Telegram-пользователь, который присоединился к GameRoom и создал персонажа.

Один пользователь может иметь одного активного персонажа в одной комнате.

Telegram User ID является основным идентификатором пользователя.

Не использовать username как идентификатор.

---

# 6. Размер карты

Размер карты рассчитывается по формуле:

```text
cells = players × 5
```

Количество игроков фиксируется при создании карты.

Примеры:

```text
1 игрок   → 5 клеток
2 игрока  → 10 клеток
5 игроков → 25 клеток
10 игроков → 50 клеток
20 игроков → 100 клеток
```

Генератор может преобразовывать количество клеток в подходящие размеры сетки.

Например:

```text
25  → 5×5
50  → 5×10
100 → 10×10
```

Карта не меняет размер при присоединении новых игроков. Новый размер определяется при следующей генерации карты.

---

# 7. Генерация карты

Каждая карта должна содержать:

- вход;
- выход;
- проходимые клетки;
- стены;
- проходы;
- комнаты;
- тупики;
- ответвления.

Обязательное условие:

```text
ENTRANCE → существует путь → EXIT
```

Генератор обязан проверять достижимость выхода.

Карта не должна быть полностью случайной сеткой.

Предпочтительно использовать генератор подземелья/лабиринта с:

- основным маршрутом;
- ответвлениями;
- тупиками;
- комнатами;
- дополнительными случайными проходами.

---

# 8. Seed генерации

Каждая карта должна иметь seed.

```text
seed
```

Seed сохраняется в базе данных.

Это позволяет:

- воспроизвести карту;
- отлаживать ошибки;
- проводить тесты;
- восстанавливать карту при необходимости.

---

# 9. Вход и выход

Каждая карта имеет:

```text
ENTRANCE
EXIT
```

Вход является стартовой точкой.

Новые персонажи появляются на входе или на ближайшей свободной клетке.

Выход может быть неизвестен игрокам.

В MVP достижение выхода позволяет завершить прохождение персонажа.

В дальнейшем выход может требовать:

- ключ;
- предмет;
- условие;
- командное действие;
- событие.

---

# 10. Персонаж

Каждый персонаж имеет:

```text
id
user_id
game_room_id
name
role
health
stamina
strength
vision_range
x
y
created_at
updated_at
```

Основные характеристики:

### Выносливость

Определяет количество ходов, которые персонаж может совершить в течение суток.

### Сила

Определяет физические возможности персонажа.

Может использоваться для:

- переносимого веса;
- взаимодействия с тяжелыми объектами;
- некоторых игровых событий;
- будущей боевой системы.

### Дальность видения

Определяет количество клеток, которые персонаж способен видеть/исследовать вокруг себя.

### Способности

Специальные действия, доступные конкретной роли.

---

# 11. Роли персонажей

В MVP реализовать четыре базовые роли:

```text
⚔️ Разведчик
🛡️ Выживший
🔧 Механик
🎒 Искатель
```

Каждая роль должна иметь базовые характеристики и уникальные способности.

Характеристики не должны быть просто косметическими — они должны реально влиять на игровой процесс.

---

# 12. Разведчик

Основная специализация:

**исследование карты и обнаружение окружения.**

Базовые характеристики:

```text
Выносливость: высокая
Сила: средняя
Дальность видения: высокая
```

Базовые способности:

### Расширенное зрение

Разведчик видит больше клеток вокруг персонажа.

### Быстрая разведка

При исследовании клетки получает больше информации об окружающих клетках.

### Следопыт

Может получать дополнительную информацию о ранее посещенных или соседних областях.

Разведчик должен быть наиболее эффективным персонажем для поиска выхода.

---

# 13. Выживший

Основная специализация:

**длительное автономное путешествие и перенос ресурсов.**

Базовые характеристики:

```text
Выносливость: очень высокая
Сила: высокая
Дальность видения: средняя
```

Базовые способности:

### Выносливость

Получает больше доступных ходов в течение суток.

### Грузоподъемность

Может переносить больше предметов.

### Живучесть

Некоторые негативные события наносят ему меньше урона.

Выживший должен быть наиболее устойчивым персонажем.

---

# 14. Механик

Основная специализация:

**оборудование, ремонт и взаимодействие с техническими объектами.**

Базовые характеристики:

```text
Выносливость: средняя
Сила: средняя
Дальность видения: средняя
```

Базовые способности:

### Ремонт

Только Механик в MVP может ремонтировать поврежденные предметы.

```text
repairItem()
```

### Техническое обслуживание

Механик тратит меньше ресурсов на обслуживание некоторых предметов.

### Инженер

Может взаимодействовать со специальными объектами карты, которые недоступны другим ролям.

Например:

- генераторы;
- механизмы;
- закрытые двери;
- технические устройства.

---

# 15. Искатель

Основная специализация:

**поиск лута и редких предметов.**

Базовые характеристики:

```text
Выносливость: средняя
Сила: средняя
Дальность видения: высокая
```

Базовые способности:

### Поиск

Получает повышенный шанс обнаружить предметы.

### Интуиция

Может получать дополнительную информацию о потенциально интересных объектах.

### Оценка

Может определять характеристики найденного предмета без дополнительных действий.

Искатель должен быть наиболее эффективным персонажем для поиска ресурсов.

---

# 16. Баланс ролей

Роли должны быть асимметричными, но не должны создавать ситуацию, в которой без конкретной роли невозможно играть.

Исключение:

**специализированные способности могут быть уникальными.**

Например:

- только Механик ремонтирует предметы;
- только Разведчик имеет максимальную дальность видения;
- только Выживший имеет максимальную выносливость;
- только Искатель получает бонусы к поиску лута.

При этом любой игрок должен иметь возможность пройти карту самостоятельно в рамках базовых механик.

---

# 17. Система ходов

Каждое перемещение персонажа является одним ходом.

Количество доступных ходов ограничено суточным лимитом.

Лимит зависит от выносливости персонажа.

Например:

```text
base_daily_moves = 20
```

и:

```text
daily_moves = base_daily_moves + stamina_bonus
```

Конкретные коэффициенты должны храниться в конфигурации, а не быть жестко зашиты в код.

Пример:

```yaml
movement:
  base_daily_moves: 20

  stamina:
    bonus_per_point: 2
```

При выносливости 5:

```text
20 + 5×2 = 30 ходов в сутки
```

---

# 18. Суточный лимит ходов

Для каждого персонажа хранить:

```text
daily_moves_used
daily_moves_reset_at
```

При каждом перемещении:

1. проверить дату/время сброса;
2. при необходимости выполнить reset;
3. проверить оставшиеся ходы;
4. списать один ход;
5. выполнить перемещение.

Важно:

**лимит должен быть серверным и не зависеть от локального времени Telegram-клиента.**

Использовать UTC для хранения времени.

Для отображения можно использовать timezone комнаты или пользователя.

---

# 19. Сброс ходов

По умолчанию доступные ходы обновляются раз в 24 часа.

Предпочтительный вариант — фиксированный ежедневный reset по UTC.

Например:

```text
00:00 UTC
```

При reset:

```text
daily_moves_used = 0
```

Фоновый scheduler может выполнять reset, но игровой движок также обязан уметь лениво сбрасывать лимит при первом действии после наступления нового периода.

Это защищает систему от пропущенных фоновых задач.

# 21. Недостаток ходов

Если лимит исчерпан:

```text
🚶 Ты больше не можешь двигаться сегодня.

Ходы: 0 / 30

Следующее восстановление:
⏰ завтра в 00:00 UTC
```

Другие действия, не являющиеся перемещением, могут оставаться доступными.

Например:

- просмотр инвентаря;
- просмотр персонажа;
- просмотр журнала;
- осмотр уже исследованной клетки;
- использование некоторых предметов.

---

# 22. Инвентарь

InventoryItem:

```text
id
character_id
item_definition_id
quantity
```

Но система должна поддерживать два типа предметов.

### Stackable

Например:

- батарейки;
- еда;
- материалы;
- медикаменты.

### Individual

Например:

- фонарь;
- инструмент;
- оружие;
- уникальный ключ;
- специальное оборудование.

Каждый individual item является отдельным ItemInstance.

---

# 23. Предметы

## ItemDefinition

```text
id
name
type
description
stackable
max_durability
weight
base_value
repairable
usable
metadata
created_at
```

## ItemInstance

```text
id
item_definition_id
character_id
durability
max_durability
created_at
updated_at
```

Два одинаковых предмета могут иметь разное состояние.

Например:

```text
🔦 Фонарь #1 — 94%
🔦 Фонарь #2 — 27%
```

---

# 24. Система износа

Предметы, которые изнашиваются, имеют:

```text
durability
max_durability
```

Например:

```text
max_durability = 100
durability = 73
```

Использование предмета уменьшает durability.

---

# 25. Состояние предмета

Condition вычисляется из durability.

```text
100–75% → GOOD
74–40%  → WORN
39–10%  → DAMAGED
9–1%    → CRITICAL
0%      → BROKEN
```

Не хранить condition как единственный источник истины.

Основное состояние:

```text
durability
```

---

# 26. Повреждение

Разделить два понятия.

### Износ

Обычное расходование ресурса.

```text
wearItem(itemId, amount, reason)
```

### Повреждение

Внештатное ухудшение состояния.

```text
damageItem(itemId, amount, reason)
```

Повреждение может происходить из-за:

- ловушки;
- падения;
- случайного события;
- неудачного использования;
- будущего боя;
- других игровых событий.

Причина изменения должна записываться в GameEvent.

---

# 27. Сломанные предметы

При:

```text
durability <= 0
```

предмет получает состояние:

```text
BROKEN
```

Сломанный предмет:

- не удаляется автоматически;
- остается в инвентаре;
- может перестать выполнять функцию;
- может занимать вес;
- может быть выброшен;
- может быть отремонтирован Механиком.

---

# 28. Ремонт

В MVP ремонт доступен только роли:

**🔧 Механик**

Другие роли не могут выполнять ремонт.

Механик может использовать:

```text
repairItem(itemId, amount)
```

Будущая система ремонта может требовать:

- инструменты;
- детали;
- материалы;
- специальные клетки;
- оборудование.

Сейчас архитектура должна позволять добавить эти ограничения без изменения модели ItemInstance.

---

# 29. Примеры предметов

## Фонарь

```text
type: EQUIPMENT
max_durability: 100
repairable: true
```

Использование:

```text
wear: -3
```

## Отмычка

```text
type: TOOL
max_durability: 10
repairable: false
```

Попытка открыть дверь:

```text
wear: -1
```

При неудаче возможно дополнительное повреждение.

## Батарейка

```text
type: CONSUMABLE
stackable: true
durability: null
```

---

# 30. Лут

Loot является объектом карты.

```text
id
map_id
item_definition_id
item_instance_id
x
y
quantity
created_at
```

Для индивидуального предмета создается ItemInstance.

Для stackable предмета хранится quantity.

---

# 31. Размещение лута

Лут нельзя размещать:

- на стене;
- на занятой клетке;
- на клетке персонажа;
- на входе;
- на выходе;
- на несовместимом объекте.

Перед размещением необходимо повторно проверить актуальное состояние карты.

---

# 32. Обновление лута

Фоновая задача:

```text
loot-respawn
```

Настройки:

```yaml
loot:
  respawn_interval: 30m
  max_items: 20
  spawn_amount: 3
```

Новые предметы появляются только на допустимых свободных клетках.

---

# 33. Персонаж и лут

После перемещения на клетку движок проверяет наличие лута.

В MVP игрок должен явно выполнить действие подбора:

```text
/loot
```

или:

```text
взять
```

Автоматически добавлять предмет в инвентарь не нужно.

---

# 34. Дальность видения

`vision_range` определяет область, которую персонаж способен видеть вокруг текущей клетки.

Например:

```text
vision_range = 1
```

видит соседние клетки.

```text
vision_range = 2
```

видит область дальше.

Разведчик должен иметь увеличенную дальность видения.

Туман войны рассчитывается сервером индивидуально для каждого персонажа.

Игрок не должен получать данные о неразведанной области через Telegram API.

---

# 35. Туман войны

Игрок видит:

- текущую клетку;
- исследованные клетки;
- доступную область в пределах vision_range;
- обнаруженные объекты.

Неисследованные области скрываются.

Пример:

```text
⬛ ⬛ ⬛ ⬛ ⬛
⬛ ·  ·  ❓ ⬛
⬛ ·  👤 ❓ ⬛
⬛ ❓ ❓ ❓ ⬛
⬛ ⬛ ⬛ ⬛ ⬛
```

---

# 36. Исследование

Каждая клетка может иметь состояние:

```text
unexplored
explored
```

Исследование должно быть привязано к персонажу.

Один персонаж может знать карту лучше другого.

Таблица:

```text
character_explored_cells
```

должна связывать персонажа и исследованные клетки.

---

# 37. Осмотр

Команда:

```text
/look
```

или:

```text
осмотреться
```

Возвращает описание текущей клетки.

Осмотр уже исследованной области не расходует ход.

# 41. Рейтинг

Рейтинг максимально простой.

Единственный показатель:

**количество пройденных игр.**

Не учитывать:

- количество найденных предметов;
- количество клеток;
- время;
- ценность лута;
- количество ходов;
- победы других игроков;
- урон;
- количество предметов.

Основная статистика:

```text
games_completed
```

Рейтинг сортируется по:

```text
games_completed DESC
```

При равенстве можно использовать вторичный технический критерий, например дату достижения результата, но пользовательский рейтинг должен показывать только количество пройденных игр.

---

# 42. Что считается пройденной игрой

Игра считается пройденной конкретным персонажем, когда он достигает выхода и успешно завершает прохождение.

Увеличивается:

```text
games_completed += 1
```

Рейтинг является долгосрочным и не сбрасывается при перестройке карты.

# 44. Что происходит при перестройке

При создании новой карты:

1. старая карта становится неактивной;
2. создается новый seed;
3. генерируется новая карта;
4. создаются вход и выход;
5. проверяется путь;
6. размещается новый лут;
7. персонажи остаются существовать;
8. их постоянный инвентарь сохраняется;
9. персонажи перемещаются к новому входу;
10. исследование старой карты сбрасывается;
11. временные объекты старой карты удаляются.

# 49. Система способностей

Способности не должны быть реализованы через проверки типа:

```typescript
if (character.role === "MECHANIC")
```

во всех местах приложения.

Использовать отдельную систему abilities.

Например:

```text
REPAIR_ITEMS
EXTENDED_VISION
SEARCH_BONUS
EXTRA_STAMINA
EXTRA_CARRY_CAPACITY
REDUCED_DAMAGE
TECHNICAL_INTERACTION
```

Персонаж получает abilities через свою роль.

Например:

```text
MECHANIC
    ├── REPAIR_ITEMS
    └── TECHNICAL_INTERACTION
```

Это позволит в будущем добавлять способности непосредственно персонажам, предметам или временным эффектам.

# 50. Формула характеристик

Характеристики должны быть числовыми.

Например:

```text
stamina
strength
vision_range
```

Базовые значения задаются ролью.

Дополнительные модификаторы могут давать:

- предметы;
- экипировка;
- временные эффекты;
- события.

Итоговая характеристика должна вычисляться движком.

Например:

```text
effectiveStrength =
    baseStrength +
    equipmentBonus +
    temporaryBonus
```

Не изменять базовую характеристику при каждом временном эффекте.

---

# 51. Грузоподъемность

Сила влияет на максимальный переносимый вес.

Например:

```text
base_capacity = 10
capacity_per_strength = 2
```

Тогда:

```text
capacity =
    base_capacity +
    strength × capacity_per_strength
```

Конкретные коэффициенты должны быть конфигурируемыми.

# 61. Конкурентность

Все критические игровые операции должны быть транзакционными.

Особенно:

- перемещение;
- подбор предмета;
- использование предмета;
- изменение durability;
- ремонт;
- обмен;
- перестройка карты;
- начисление games_completed;
- списание дневного хода.

Необходимо исключить race conditions.

Пример:

```text
Игрок A ─┐
         ├── пытаются взять один предмет
Игрок B ─┘
```

Предмет получает только один игрок.

Использовать PostgreSQL transactions и row-level locking / atomic operations.

---

# 62. Идемпотентность

Telegram updates должны обрабатываться идемпотентно.

Повторная доставка одного Telegram update не должна:

- списать два хода;
- выдать два предмета;
- увеличить рейтинг дважды;
- дважды выполнить ремонт;
- повторно завершить игру.

---

# 63. Telegram handlers

Handlers только преобразуют Telegram update в Application Service.

Пример:

```typescript
bot.command("inventory", async (ctx) => {
    const character =
        await characterService.getCurrentCharacter(...);

    const inventory =
        await inventoryService.getInventory(character.id);

    await ctx.reply(formatInventory(inventory));
});
```

Игровая логика должна находиться в Game/Application Services.
